# 《树碑立传》PDF 转为 RAG 数据库：难度评估

- **评估对象**：`树碑立传：吴中古树名木的故事教育读物(1).pdf`（234 MB）、`博物馆年报（用户画像）.md`
- **方法**：先对全书逐页扫描（文字层、字体、版式、图片），再对"树的故事"整章做了一次结构化抽取试验，并抽查其他章节
- **配套文件**：[pilot/stories.jsonl](pilot/stories.jsonl)（105 个条目的试验输出）、[scripts/pilot_stories.py](scripts/pilot_stories.py)、[scripts/pdf_scan.py](scripts/pdf_scan.py)
- **日期**：2026-11-03

---

## 0. 结论

**总体难度：中等。** 难点不在"把字取出来"，而在"把结构取对"。

- **容易的部分**：PDF 是 InDesign 直接导出的，文字层完整，不需要 OCR。试验章节的文字覆盖率实测为 100%（45,817/45,817 个汉字）。全书排版样式高度规范（固定字体、字号、颜色、栏位），可以用规则准确还原。
- **难的部分**：
  - 几乎每页都是对开页、分栏排版，条目跨栏跨页。
  - 访谈侧栏和图注用的是同一种字体。
  - 各章节版式不同，部分编号字体的 Unicode 映射损坏。
  - 同一棵树散落在多个章节里。
  - 书内存在自相矛盾的说法，还混有传说、口述和随笔，需要标注内容类型和可信度。

**三种做法的对比**：

| 做法 | 工作量 | 效果 |
|---|---|---|
| L0：整本直接抽文字、切块、入向量库 | 约半天 | **不推荐。** 试验第一版用的就是朴素解析，结果 105 个条目中 104 个的地点被挂到了下一个条目上（最后一个缺失）。AI 会据此把"光福铜观音寺"说成 18 号古柏的所在地。图注和访谈也会混进正文，切块会跨条目。 |
| L1：按章节版式解析，按条目/文章切块，每块带元数据 | 约 5–8 人日（含抽检） | **推荐作为 MVP。** 其中"树的故事"一章已在试验中完成：105/105 个条目的编号、地点、树种、正文和访谈侧栏全部正确。 |
| L2：在 L1 基础上建结构化知识库（树木实体表、事实条目、来源、冲突标注，并与现场资料关联） | 全书约 2–3 周，且依赖馆方核实 | 建议只对重点树做：我们的 3 处 6 株，加上馆方指定的重点树。 |

**规模**：全书约 17 万汉字（总计 21 万字符）。按每块 300–600 字切分，约 400–600 块，对向量库来说规模很小，不存在性能或成本问题。

**最有效的省力办法**：先向馆方要排版源文件（InDesign/IDML）或原始 Word 稿。拿到源文件，大部分版式还原工作就可以省掉（见 §5）。

## 2. 试验：把"树的故事"整章结构化

**做法**：用字体、字号、颜色和坐标来识别元素角色：

- 编号：Times 18pt 白色
- 地点：8pt 灰色
- 树种标题：14pt 绿色
- 正文：方正书宋 8.5pt
- 侧栏和图注：楷体 7pt

然后按"半页 → 栏 → 行"重建阅读顺序，按条目头切分，按 17pt 首行缩进识别段落。

**结果**：

| 指标 | 结果 |
|---|---|
| 条目识别 | 105/105，编号无缺失、无重复 |
| 地点和树种 | 105 个条目都有地点；与图片页图注抽查一致 |
| 文字覆盖率 | 100%（45,817/45,817 个汉字；已扣除页眉页脚） |
| 访谈/手记侧栏 | 21 段；识别出 7 个说话人，如"吴博馆员""宽尘法师""古树保护工作者"等 |
| 已不存在的树 | 自动标出 4 条（14、29、34、74），可作为 status 字段的初值 |
| 文中出现的官方编号 | 只有 11 个条目在正文里写了编号（如吴中076、狮012、沧553、网003） |

**输出示例**（18 号，节选）：

```json
{
  "entry_no": 18,
  "location": "光福司徒庙",
  "title": "圆柏",
  "pdf_pages": [47],
  "text": "……苏州生长状态最好、树龄最长、最负盛名的古柏为光福司徒庙四棵“清、奇、古、怪”汉柏，树龄均为1900岁。……翻阅文献，“邓禹手植”“乾隆赐名”等说法并无明确依据……",
  "captions": ["吴县文管会保留的清奇古怪古柏档案。"],
  "status_gone": false
}
```

**试验中发现并修好的问题**（这些正是 L0 做法会踩的坑）：

1. **条目头错位**：地点行比编号圆圈高几个点，按纵坐标排序时会排到上一个条目里。第一版因此几乎全部挂错，改为"条目头簇重排"后修好。
2. **行内数字基线偏移**：数字和英文用 Garamond，基线和汉字差约 1pt，会被拆到别的行（实际出现过"共有 棵古树：吴中6334"这样的错误）。改为按行的垂直中心聚类后修好。
3. **侧栏与图注同字体**：按行数区分（1–2 行为图注，≥3 行为侧栏）。跨栏的侧栏需要合并，否则一句话会被截成两段（宽尘法师访谈曾被截断）。
4. **数字与汉字之间多余的空格**：例如"1924 年"，已统一去除。

**还没处理的问题**：

- 少数条目的绿色标题不是树种。例如 34 号标题是"一棵枫杨的生与死"，需要从索引表或图片页图注取树种。
- 有的条目包含多个地点或多种树。例如 23 号写了两个园林；6 号写了"香樟、紫藤、杨梅"；18 号一个条目对应 4 株树。

## 3. 难点清单

| # | 难点 | 本书中的例子 | 不处理的后果 | 解决办法 | 难度 |
|---|---|---|---|---|---|
| 1 | 对开页、分栏、条目跨栏跨页 | 187 页为对开；PDF 第 47 页一页内含 18、19、20 三个条目 | 读序错乱，切块跨条目 | 按半页 → 栏 → 行重建阅读流，按条目边界切块 | 中（故事章已解决） |
| 2 | 条目头元素错位 | 地点行位于编号圆圈上方 | 地点张冠李戴 | 条目头簇重排 | 低（已解决） |
| 3 | 侧栏与图注同字体 | 楷体 7pt 同时用于图注和访谈框 | 访谈被丢弃或混入正文 | 按行数和位置区分，跨栏合并 | 中（已解决） |

| 6 | 竖排和加字距标题 | 17 页有竖排行或加字距标题（如"古 树 的 信 仰"） | 标题识别错误 | 去除字间空格，竖排单独处理 | 低 |

## 4. 推荐的入库方案（L1）

### 4.1 按章节决定切分单位

| 章节 | 文档单位 | 切块方式 | content_type |
|---|---|---|---|
| 树的故事 | 一个条目 | 条目中位长度只有 380 字，多数整条为一块；超过 600 字的（17 条）按段落切分。每段侧栏单独成块，访谈按问答对切分 | `story` / `interview` / `fieldnote` |
| 各区索引与图片页 | 一行（编号、区县、地点、树种、状态） | 不进向量库，进树木实体表 | — |
| 古树与艺术 | 一件作品 | 作品信息块进结构化字段；"艺术家""策展人"各一块 | `art` |
| 志愿者活动与走访 | 一篇文章 → 一个小节（"地点——树种"） | 按段落切块，小节头里的编号和树龄进元数据 | `fieldnote` / `oral` |
| 研究性文章 | 一篇文章 → 一节 | 按段落切块（约 500 字）；文章的参考文献列表作为来源挂到每个块上 | `essay` |
| 前言、导论 | 一篇 | 按段落 | `intro` |

### 4.2 每个块的元数据

```json
{
  "chunk_id": "story-018-01",
  "source": "树碑立传：吴中古树名木的故事（吴文化博物馆，2024）",
  "section": "树的故事",
  "entry_no": 18,
  "tree_ids": ["吴中186", "吴中187", "吴中188", "吴中189"],
  "tree_ids_via": "艺术章节 p88 关联",
  "site": "光福司徒庙",
  "district": "吴中区",
  "species": ["圆柏"],
  "content_type": "story",
  "status": "alive",
  "printed_page": 92,
  "pdf_page": 47,
  "flags": ["legend:邓禹手植", "legend:乾隆赐名"],
  "text": "苏州生长状态最好、树龄最长、最负盛名的古柏为光福司徒庙四棵……"
}
```

引用时使用**印刷页码**（页脚中的数字，可以可靠抽取），方便观众和馆员翻书核对。

### 4.3 数据库选型

- **规模很小**：原型用 SQLite（结构化表 + FTS5 关键词检索）加一个向量索引（sqlite-vec、Chroma 或 FAISS 都可以）。部署时可以用 PostgreSQL + pgvector，把结构化表和向量放在同一个库里。
- **检索**：必须做关键词 + 向量的混合检索。地名、树种、编号（如"吴中203""甪直"）需要精确匹配，单靠向量检索容易漏掉。
- **向量模型**：bge-m3（开源，中文效果好，可以本地部署）。
- **表结构**：`trees`（实体）、`sites`、`chunks`、`sources`、`conflicts`，与上一份方案的知识库设计保持一致。

### 4.4 对上一份方案的调整

- 上一份方案建议 MVP 采用"单树全文放进上下文"，因为当时只有 3 棵树，每棵不到 5 千字。现在有了这本书（105 个条目、约 30 篇文章、约 17 万字），**需要检索**：用"按树/地点做元数据过滤 + 混合检索"，结构化事实仍然直接查表。
- 本书是博物馆自己编辑出版的资料，可信度高于上次的 docx。三棵树的知识条目应该改为以本书为主要来源。
- 需要补充向馆方确认的问题：
  1. 能否在面向公众的 AI 应用里直接引用书中原文？
  2. 能否提供 IDML 或 Word 原稿和原图？
  3. 雪松种植年份（1923 还是 1924）、憨山复创时间（1569 还是 1596）、石楠"800余年"与"元朝"，馆方采用哪种口径？

## 6. 建议的下一步

1. **先向馆方要源文件**：IDML 或 Word 原稿，以及原图。这能把解析工作从几天缩到半天，也能解决图片分辨率和授权问题。
2. **拿不到源文件就继续用 PDF**：在试验脚本的基础上补完其余章节（走访页的栏检测、艺术作品信息块、研究文章的参考文献），产出全书的 `chunks.jsonl`。
3. **建树木实体表**：先覆盖我们的 3 处 6 株和馆方指定的重点树，把条目号、官方编号、地点和别名对齐。
4. **做 30–50 题的检索测试集**：包括冲突题（"憨山哪年来石壁？"）、已死亡的树（"海云院的山茶还在吗？"）、跨章节题（"吴中203 有哪些艺术作品？"），用来评估切块和检索效果。
